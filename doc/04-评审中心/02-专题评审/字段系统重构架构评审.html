字段系统重构架构评审

本页用于字段系统重构实施前后评审：检查边界、不变量、legacy 风险、图片与多值字段能力是否按统一架构落地。

状态：当前有效最后更新：2026-05-21格式：HTML

架构评审结论模板

字段系统重构只有在满足以下条件时才允许进入下一阶段：核心不变量通过测试，新增字段能力走统一 FieldDefinition，旧兼容逻辑集中且带 legacy 标记。

实施前检查

检查项通过标准
边界清晰字段类型、语义、来源、存储四个概念已经在代码类型中分开。
不变量保护header/theme、themePath、extra 去污染有单测和静态检查。
迁移策略legacy 字段只读、默认隐藏、不写回；cache schema 有升级计划。
UI 风险字段配置器先兼容旧设置，不强迫一次性迁移所有用户配置。
回滚策略Phase 0/1/2 可独立回滚；不破坏 Markdown 原始数据。

架构风险

风险影响缓解
过早重写全部 UI工期失控，功能回归。先建立 resolver/registry，再逐步替换 UI。
FieldDefinition 太重配置复杂，用户难理解。高级项折叠；普通用户只看类型、名称、选项。
legacy 逻辑继续扩散旧问题复活。所有 legacy alias 集中在 FieldMigration/Codec，不进 UI 层。
extra 清理导致旧字段看不见用户误以为数据丢失。字段来源面板显示“历史自定义字段”；提供显式迁移按钮。
图片字段与 Obsidian 资源路径不兼容图片预览失败。支持 vault path、wikilink、URL 三种 kind。

必须拒绝的实现方式

  • 继续在 readField() 里无限添加字段特殊判断。
  • 继续在 UI 组件里通过字段 key 判断图片、主题、标签。
  • 继续把 heading/header 当成 theme/category 的 fallback。
  • 继续把 parser 自动 alias 暴露为用户 extra 字段。
  • 在没有迁移报告的情况下删除 legacy 字段读取能力。

评审通过标准

层级标准
类型层新增字段不需要修改多个 if/else，而是注册 FieldDefinition。
解析层同一个字段在 task/block 中有统一 codec 行为。
视图层筛选、排序、显示都通过 FieldValueResolver。
迁移层旧 theme/pintu/extra alias 有明确迁移路径。
测试层新增字段类型必须有 parser、resolver、renderer、filter 测试。
