2026-05 字段系统高质量完成线改造计划

本计划把字段系统重构拆成可执行阶段：先彻底修正 header/theme、themePath 筛选、extra 污染，再进入字段分类、类型语义分离、图片与多值层级字段、迁移验收。

状态：当前有效最后更新：2026-05-21格式：HTML

一句话目标

把“字段”从散落的配置项、解析别名、UI if/else、搜索派生字段中抽出来，升级为 Think OS 的一级架构对象。完成后，每个字段都必须能回答四个问题：它是什么类型、承担什么语义、存在哪里、值从哪里来。

本轮硬约束：header 永远不参与 theme；筛选里的主题统一指 themePath；extra 只接收显式未知 KV，且来源可解释。

高质量完成线

维度完成标准不可接受情况
字段模型存在统一 FieldDefinition、FieldType、FieldSemantic、FieldOrigin，核心字段、文件字段、派生字段、extra 字段有清晰分类。继续靠字段名猜语义，例如字段名叫“主题”才被当主题，字段名叫“标签”才被当标签。
来源追踪任意记录字段都能说明来自 Markdown task KV、block KV、tag、heading、file stat、template default、derived、cache 或 legacy。用户看到一个字段，但不知道它是设置生成、历史遗留、解析器自动写入还是从文件属性推导。
读写对称Markdown -> Record -> FormData -> Markdown 走统一 codec，编辑不丢字段、不重复字段、不把历史 fallback 写回新数据。解析逻辑、编辑回填、模板渲染各写一套规则。
筛选搜索筛选、排序、搜索统一通过字段解析器和索引定义，不绕过字段语义。主题筛选默认使用 themePath。视图筛选直接读 item.theme || item.header 或在 UI 层拼派生值。
图片与多值图片、多图、多选、层级路径、多标签成为基础字段能力，而不是 pintu 或 rating 特例。图片只能靠字段 key 名判断，或只能在某一个业务字段上预览。
测试验收有单元、集成、迁移、回归、手动 Obsidian 场景清单；cache schema 升级有测试。只靠手动试用，无法防止 header/theme、extra 污染回归。

分模块落地顺序

顺序代码模块为什么先做产物
1src/core/types先定合同，避免 UI 和 parser 继续各自发明字段。FieldDefinition、FieldOrigin、FieldCategory、RecordFieldValue 类型。
2src/core/fields集中字段注册、解析、默认显示、过滤能力。FieldRegistry、FieldValueResolver、FieldOriginCollector。
3src/core/utils/parser.ts 与 codec控制字段进入系统的入口，解决 extra 污染。Task/Block codec、known key mapping、legacy alias mapping。
4src/core/services/DataStore.ts扫描和缓存是数据真源，先确保 Item 干净。字段来源注入、cache version、派生字段统一。
5recordInput 与 InputService编辑回填和写入必须与解析对称。FormData mapper、OutputPlanner 接字段定义。
6settings / filters / viewEditors让用户看到的新字段体系可配置、可筛选。字段分类 UI、themePath 筛选、extra 来源提示。
7shared ui / QuickInput最后替换显示和输入控件，风险较低且可逐步迁移。通用 FieldRenderer、ImageField、MultiTagField。

退出条件

  • 用户可以在字段选择器中清楚看到：核心字段、文件字段、语义字段、派生字段、自定义字段、历史兼容字段。
  • 点击任意字段可以看到来源说明，至少包含来源类型、原始 key、文件路径、行号、显式/派生/历史置信度。
  • 新建字段时先选字段类型，再选可选语义；字段 label/key 可以自由命名。
  • 主题、分类、标签都作为“层级路径 / 多值标签”能力存在，不绑定固定字段名。
  • 图片字段可作为任意字段定义使用，不再依赖 pintu 特例。
  • 旧数据能继续搜索显示，但 legacy 字段默认隐藏，不再污染新数据。
本页属于 Think OS 插件 HTML 文档系统。字段系统改造原则：字段名称自由、字段类型固定、字段语义显式、字段来源可追踪。
