Goal/Cycle/Record 关系模型

把产品层的目标闭环翻译成后续开发可落地的最小技术模型，先定义关系，再决定旧 Block、Task、Statistics 如何接入。

状态：重定位草案 最后更新：2026-05-13 格式：HTML

技术目标

第一阶段不急着重排目录，而是先建立一套能解释现有记录的关系层。旧的计划 Block、总结 Block、任务、Timer 记录和 Statistics 数据，都要能逐步映射到目标闭环，而不是继续作为互不相干的能力。

核心原则：先做可追溯关系，再做目录和 UI 重构。

最小实体

实体建议最小字段说明
Goalid, title, status, themeId, metric, createdAt, updatedAt目标是一等公民，不能只靠主题或标题推断。
Cycleid, goalIds, title, startDate, endDate, status周期是推进窗口，可承接一个或多个目标。
Planid, goalId, cycleId, sourceBlockId, content, status计划可以继续以 Block 呈现，但要有关系字段。
Taskid, goalId, cycleId, planId, content, status, dueDate任务必须能追溯到目标，计划关联可以后补。
Recordid, goalId, cycleId, taskId, recordType, startedAt, endedAt, content统一承载执行、时间、阻塞、产出等证据。
Reviewid, goalId, cycleId, sourceBlockId, summary, adjustments总结 Block 映射为周期复盘角色。
FeedbackgoalId, cycleId, metrics, signals, generatedAt可以是派生结果，不一定持久化为用户文件。

旧数据映射

现有来源映射目标迁移策略
计划 BlockPlan先补 recordRole=plan、goalId、cycleId，保留原 Markdown 内容。
总结 BlockReview先补 recordRole=review，让它能读取同周期任务和记录。
任务行Task保留现有任务写回逻辑，新增目标和周期上下文。
Timer 记录Record作为 recordType=time 的执行证据。
QuickInput 输入Task 或 Record作为入口，不作为独立领域模型。
Statistics ViewFeedback改为按目标和周期聚合任务、记录、复盘。
主题 ThemeGoal.themeId 或筛选维度主题只做分类，不替代目标。

读写边界

  • 第一版优先追加关系字段，不做破坏性迁移。
  • Markdown 原文仍是用户可见和可恢复的资料来源。
  • 关系模型可以先以解析层或索引层存在，不急着改变所有文件格式。
  • 写入逻辑必须能处理缺失关系：允许临时记录，但要提供后续补齐上下文的入口。
  • Statistics 先读新关系，读不到时降级读取旧字段。

开发前检查

问题必须回答
数据从哪里来？目标、周期、计划、任务、记录是否都能从现有 Markdown 或插件状态中读出。
写回写到哪里？新增关系字段是否不会破坏旧任务和 Block 内容。
缺失关系怎么办？是否能标记为未关联并提供补齐路径。
统计如何解释？是否先按目标和周期聚合，再展示数字。
旧资料如何保留？QuickInput、字段、迁移资料继续作为实现参考，不作为产品主线。
