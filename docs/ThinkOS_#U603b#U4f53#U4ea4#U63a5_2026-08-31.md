# 1. 产品全貌：不是几个 View，而是一张个人运行关系网

Think OS 有两条闭环，但共用同一批事实。

```text
                         Goal
                  我想把资源投向哪里
                           │
               ┌───────────┼───────────┐
               ▼           ▼           ▼
             Plan        Habit      TaskSeries
               │           │           │
               └──────┐    │    ┌──────┘
                      ▼    ▼    ▼
                         Task
                     我准备做什么
                           │
                           ▼
                     TaskSession
               我实际做了什么 / 做了多久
                           │
            ┌──────────────┼──────────────┐
            ▼              ▼              ▼
          Energy          Habit          Thought
        前后状态变化      行为完成       当次体验/想法
            │              │              │
            └──────────────┼──────────────┘
                           ▼
                     同一次真实经历
                   （概念，不新增RecordType）
                           │
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
       Evidence          Blocker          Review
        变化证据           阻碍             解释/复盘
          │                │                │
          └────────────────┼────────────────┘
                           ▼
                       Milestone
                       长期变化节点
                           │
                           ▼
                          Goal
                      调整下一轮方向
```

### 两条闭环

**行动闭环**

```text
Goal / 时间意图
      ↓
当前状态 + 可做任务 + 最近执行
      ↓
决定下一步
      ↓
Task → Timer → TaskSession
      ↓
留下最低成本的可靠事实
```

它回答：

> **我现在做什么？应该把时间投到哪里？什么时候该继续/停止？**

**理解闭环**

```text
TaskSession
   + Energy
   + Thought / Experience
   + Habit / Evidence
        ↓
   单次经历的影响
        ↓
   多次后的模式
        ↓
Review / Milestone / 长期变化
        ↓
重新理解 Goal
```

它回答：

> **这件事当时怎样影响我？为什么每次体验不同？长期以后我有什么变化？**

### Record 之间应逐步建立的关系

| 来源 | 关系 | 去向 | 含义 |
|---|---|---|---|
| Goal | contains / belongsTo | Plan、Habit、Task、Review、Evidence、Milestone | 所有行为最终服务于什么 |
| TaskSeries | instantiates | Task | 周期规则产生本次任务 |
| Task | executedBy | TaskSession | Task 是意图，Session 是实际执行事实 |
| TaskSession | startState / endState | Energy | 这一次执行前后状态 |
| TaskSession | fulfills | Habit | 同一次行为可同时完成习惯 |
| TaskSession | experiencedAs | Thought / Experience | 这一次的主观体验 |
| TaskSession | produces | Evidence | 这一次产生的客观变化/结果 |
| Review | reviews | 一段时间 / 一组 Record | 对经历进行解释 |
| Milestone | supportedBy | Evidence / Review | 长期变化有事实依据 |

**现在不新增 Episode RecordType。**  
“同一次经历”先作为关系层概念。只有未来现有 Record + Relation 无法表达时，才重新评估是否需要新 RecordType。

### View 的边界

| UI | 只负责回答 |
|---|---|
| Goal | 我为什么做；我希望资源怎么分 |
| Timeline | 时间实际上去了哪里 |
| Energy View | 我现在适合做什么；什么事情恢复/消耗我 |
| Table | 查询、筛选、找到历史 Record |
| QuickInput | 创建/编辑模板型 Record |
| Timer | 当前执行 |
| AI Chat | 查询、讨论、复盘；以后提出需要确认的操作 |

**业务能力属于 Domain，不属于 View。**  
不做“今日调度”新 View，不让 Timeline / Energy / Table 各自实现一套推荐、时间统计或 Record 创建逻辑。

# 2. 当前基线与已经冻结的决定

| 项目 | 当前结论 |
|---|---|
| 当前代码线 | **1.0.73 + Hotfix 2 cumulative patch** |
| done Task ▶ | 已设计为“再次执行”，不篡改历史 done 事实 |
| Timer Energy | 已改为单次「精力」按钮；前后 Energy 属于本次 TaskSession，不属于 Task 永久属性 |
| 精力面板 | 已简化；不重复任务名、不加冗余注释 |
| Record Capture Runtime | Goal 默认值、user-owned empty、AI/调用值优先、场景语义已做过收敛 |
| Goal 连切 50 次 | 用户曾真实验收过；之后出现过回归，Hotfix 2 已针对数组 hydrate 循环修复，**新窗口不要把它自动视为最终通过，按本地现状判断** |
| Table / QuickInput 空白 | 已确认更可能是 **Sparse Markdown Record 字段少导致恢复失败**，而非某个 View/RecordType 专属问题；**当前暂不处理** |
| 完成任务结束精力 | Hotfix 2 已针对 Timer 删除后误关闭结束采样修复；按本地实际结果判断 |
| AI 9/10/11 | 作为 Record Capture 回归维护，不作为当前主线 |
| AI Input → AI Chat | 最终方向合理，但**现在不做** |
| Task Organizer | 已取消，不再开发 |
| RoutineInference | 忘记开始/结束、高频行为补录方向明确，但**现在不做** |
| 全局主动建议 | 不做；未来第一阶段主动建议只放 **Energy View** |

## 核心工程原则

1. **Task ≠ TaskSession**
   - Task：我要做什么。
   - TaskSession：我实际上做了什么、做了多久。
   - 时间统计只认 TaskSession。

2. **单次事实 ≠ 长期结论**
   - 同一个 Task 第一次可能恢复精力，第二次可能消耗精力。
   - Energy effect 记录在 occurrence / Session 层，不固化在 Task。

3. **记录 ≠ 现实**
   - 长期需要区分 occurredAt / recordedAt / confirmedAt，以及用户事实、系统事实、推断事实。
   - 但这不是当前版本要实现的内容。

4. **先降低摩擦，再增加智能**
   - 能从现有事实自动算的，不要求用户再填。
   - AI 不应该成为确定性规则的前置依赖。

5. **防 XY Problem**
   - 每次开发前都问：原始问题是什么？现有能力已经解决多少？真正只缺什么？
   - 功能完成后重新验证原始摩擦有没有下降。

# 3. 1.0.74：Goal 时间预设与时间平衡基础（当前最高优先级）

## 原始问题

> **我需要先表达“一个正常生活周期希望长成什么样”，并把真实 TaskSession 放回这个结构里观察。这个预设不是排日程，也不是要求现实严格执行计划。**

当前版本只建立稳定的时间预设与 Balance Signal，不判断“长期是不是把时间投错方向”，也不直接控制 Energy Recommendation。

## 产品契约

### 100% 的定义

**顶层 Goal 的 100% = 一周自然时间 168h。**

不是：
- “可用时间”；
- 已记录 TaskSession 总时间；
- Task.expectedDuration；
- scheduledAt / 计划块。

因此：

```text
顶层 Goal 周目标时间 = 168h × timePresetPercent
```

例如：

```text
休息 40% = 67.2h / 周
```

### 顶层 Goal：百分比 + 自动换算时间

顶层 Goal 独立编辑百分比，**不再联动修改其它 Goal**。

允许所有顶层显式预设合计 `< 100%`。差额自动成为：

> **预留时间**

预留不是 Goal，也不要求用户解释；系统只保证：

```text
显式顶层预设 + 预留 = 168h
```

如果显式顶层预设超过 100%，阻止保存并提示超额；绝不偷偷压缩其它 Goal。

### 子 Goal：可选周目标时间，不显示百分比树

子 Goal 不再强制“父内百分比合计 100%”。

需要稳定保障时间的子 Goal，可直接设置：

```text
weeklyTargetMinutes
```

例如：

```text
休息 42% · 70h34m/周

  睡眠      56h/周
  吃饭       7h/周
  运动       4h/周
  体检         —
  未细分   3h34m
```

“体检”可以完全没有时间预设；发生时只留下 TaskSession 事实。

对子 Goal：

```text
有预设的直接子目标合计 + 未细分 = 父目标总目标时间
```

**未细分是自动余额，不是 Goal，不是用户输入。**

不强迫用户把父目标全部解释成子 Goal；但数学上始终闭合。若子目标预设合计超过父目标，阻止保存，不自动改其它数字。

### Task cadence 与时间预设分离

日 / 周 / 月 / 季 / 年周期属于 Task / TaskSeries 的发生规则，不属于 Goal 时间预设。

例如一年一次体检：
- 不按周摊销；
- 不需要时间预设；
- 实际发生 4h 时，TaskSession 正常计入对应 Goal actual。

### 实际时间唯一事实来源

```text
TaskSession
→ Task
→ goalPath
→ Goal 及祖先 Goal roll-up
```

不使用：
- Task.expectedDuration；
- scheduledAt；
- 计划块；
- 没有 Session 的 legacy Task start/end；
- 创建了但没有执行的 Task。

TaskSession 没有可解析 Goal 时，显示为：

> **未归属时间**

不要与设置页的“预留 / 未细分”混用。

### 时间平衡：默认 ±10% 不打扰区

全局默认：

```text
TIME_BALANCE_TOLERANCE_RATIO = 0.10
```

它表示**正常波动的静默区**，不是睡眠健康底线、最大值或硬约束。

对有时间预设的 Goal：

```text
lower = target × 90%
upper = target × 110%
```

Balance Signal 可为：
- balanced；
- low；
- high；
- pending / unconfigured。

当前周期未结束时，比较应按“截至当前时间的应有进度”评估，避免周一就拿实际值与完整一周目标直接比较。

### 年 / 季 / 月 / 周 / 天

只维护**一份时间预设**，不同 Timeline 尺度按自然时间换算目标：

```text
天：24h × 顶层比例
周：168h × 顶层比例
月：本月自然天数 × 24h × 顶层比例
季 / 年：对应自然天数 × 24h × 顶层比例
```

子 Goal 的 weeklyTargetMinutes 同样按自然时间比例换算到当前范围。

### Timeline UI 边界

**不新增 View，不替换原 Timeline 信息架构。**

- 年 / 季：继续使用原来的 `月份 | 月度总结 | W1...W5` Summary Table；Goal 时间信息进入原单元格。
- 月 / 周 / 天：继续使用原 Timeline + 顶部总结。
- 默认一行：`Goal + 实际时间 + 极简条形`。
- 目标时间、实际时间、差值、±10% 平衡范围、子目标明细放悬浮 / 点击详情。
- 主界面优先讲“小时”，不暴露 `effectivePercent / pp / 父内比例` 等工程字段。

Goal 设置保持紧凑，并在编辑过程中实时反馈余额：
- 顶层：`[50] % 84h/周`，输入框只包数字，单位与换算时间放在输入框外；
- 子层：`[4] h/周`，只显示/编辑时间，不显示百分比；
- 设置页顶部只突出全局余额：`剩余 Xh` / `超出 Xh`，悬浮再显示“已预设 + 余额 = 168h”；
- 展开的父 Goal 子列表末尾显示实时余额：`未细分 Xh` / `超出 Xh`，悬浮再显示“子目标预设 + 未细分 = 父目标总时间”；
- 父 Goal 主行不再重复显示未细分信息。

### Energy Recommendation 边界

**1.0.74 不改变 Energy Recommendation 排序。**

本版只让 Domain 产出可消费的 `balanceState / targetMinutes / actualMinutes / differenceMinutes`。

后续 1.0.75 再把 Goal Balance 作为 soft ranking signal，与现有：
- urgency / priority；
- energy fit；
- recent action；
- duration；
- personal history
一起参与决策。

Balance 不能直接禁止任务，也不做全局 Toast/系统通知。

## 1.0.74 完成标准（修订）

1. 顶层百分比按自然一周 168h 换算周目标时间。
2. 顶层编辑只改自己，不联动其它 Goal。
3. 顶层显式预设可小于 100%，差额自动显示预留；超过 100% 阻止保存。
4. 子 Goal 可选设置 weeklyTargetMinutes；没有预设完全合法。
5. 子目标预设 + 自动“未细分”始终等于父目标总目标时间。
6. 子目标合计超过父目标时阻止保存，不偷偷修改已有数字。
7. 年任务/一次性任务不摊销；发生时 Session 正常计入 actual。
8. actual 严格只来自 TaskSession，并正确 roll-up 到祖先 Goal。
9. 无 Goal Session 显示为未归属。
10. 默认 Balance 容差为 ±10%，当前周期按截至当前进度评估。
11. 年/季恢复并沿用原 Summary Table；月/周/天沿用原 Timeline。
12. UI 默认一行；主信息以时间为主，工程比例隐藏到详情。
13. 不修改 Energy Recommendation。
14. 当前为单用户单数据集，**不做旧 weeklyBudgetPercent 兼容迁移**。
15. 不顺手实现 Sparse Markdown、RoutineInference、AI Chat 合并等暂缓项。

# 4. 之后的整体路线

下面是**能力顺序**，不是要求一次全部实现。完整架构可以看远，实际版本每次只承诺一个可验证变化。

| 阶段 / 可能版本 | 原始问题 | 关键能力 | 用户能直接感觉到的变化 | 主要 UI |
|---|---|---|---|---|
| **1.0.74 时间预设** | 一个正常生活周期希望长成什么样？ | **168h 顶层时间预设 + 可选子目标时间 + TaskSession actual + ±10% Balance Signal** | 能表达时间结构，并在原 Timeline 中看到目标时间与实际时间 | Goal + Timeline |
| **1.0.75 决策质量** | 现在做什么更合理？ | Energy fit + Goal balance signal + priority + 最近行动 | 推荐不再只看“能不能做”，还看“该不该继续投这里” | Energy View |
| **1.0.76 主动但克制** | 我打开插件时，能不能少想一步？ | ContextSnapshot + 2~3 个确定性 Rule | Energy View 最多出现 1–2 条可执行建议：继续 / 开始 / 收尾 | Energy View |
| **之后：低摩擦事实** | 高频行为中忘记开始/结束怎么办？ | Routine / Session inference、历史模式、一键修正 | “这个 Session 可能早该结束”“这次高频活动要补吗？” | Timer / Energy / 现有入口 |
| **之后：经历关系** | 时间和 Energy 还是不能说明“这次发生了什么” | TaskSession ↔ Habit / Energy / Thought / Evidence Relation | Timeline 展开一次执行能看到行为、状态、体验、结果 | Timeline + Domain |
| **之后：体验采样** | 同一任务每次感觉为什么不同？ | 结束时可选一句 Experience | 一次行动除了多久、精力变化，还能留下主观体验 | Timer 结束流程 |
| **之后：模式理解** | 什么通常恢复我、消耗我？ | occurrence effects + aggregation + context differentiation | Energy View 显示最近 N 次影响、均值和波动，不覆盖单次事实 | Energy View |
| **之后：长期成长** | 几个月后我到底变了什么？ | Evidence / Review / Milestone longitudinal model | 能看到行为、体验、能力、状态怎样长期变化 | Review / Progress |
| **之后：AI 复盘** | 这些事实说明什么？下一步怎么调整？ | AI Chat 读取整张关系网；Action Proposal 需确认 | 可以和 AI 有来有回地复盘真实数据，而不只是“帮我建任务” | AI Chat |

### 暂缓但不遗忘

**Sparse Markdown / QuickInput Compatibility**

已判断：历史 Markdown 字段少时，Record 恢复逻辑可能假设字段完整，导致 QuickInput 空白。  
正确的长期问题定义是：

> **任何能识别 RecordType + 主内容的稀疏历史 Record，都应该支持 parse → edit → save round-trip。**

当前明确暂不处理，避免 1.0.74 再次变成“顺手修一切”。

**RoutineInference**

忘记开始/结束不是优先交给 AI 猜，而是优先利用：

- 高频行为
- 历史时间窗口
- 当前/后续 Session
- Task 完成时间
- Habit 完成事实

产生高置信度修正建议：

```text
历史 + 当前事实
      ↓
RoutineInference
      ↓
提出修正候选
      ↓
用户一键确认
```

当前明确暂不做。

新窗口读完这份文档后，先保持当前 Feature Contract，不重新把时间预设解释成“可用时间预算”或“兄弟 Goal 强制 100%”。

1. 顶层百分比基于自然一周 168h。
2. 顶层独立编辑，允许 `<100%`，差额自动成为预留；禁止 `>100%`。

4. 子目标预设 + 自动未细分 = 父目标目标时间；不强迫解释全部时间。
5. 年度/一次性 Task 不摊销；发生时只通过 TaskSession 进入 actual。
6. actual 只认 TaskSession，并向祖先 Goal roll-up。
7. 全局平衡容差 ±10%，只是“不打扰区”，不是健康底线或硬约束。
8. 年/季沿用原 Summary Table；月/周/天沿用原 Timeline；默认一行，细节 hover/click。
9. 1.0.74 不改变 Energy Recommendation，只产出 Balance Signal；1.0.75 再消费。
10. 当前单用户单数据集，不做旧 weeklyBudgetPercent 兼容迁移。

开场可以直接说：

> 我们继续 Think OS。1.0.74 当前定义是“时间预设与时间平衡基础”，不是周排程器。
>
> 顶层 Goal 百分比基于自然一周 168h；允许留预留。子 Goal 只对需要稳定保障的项目设置周目标时间，未设置完全合法；剩余自动显示未细分并与父目标总时间闭合。实际只认 TaskSession。默认 ±10% 为静默区。
>
> Timeline 必须长在原来的年/季 Summary Table 和月/周/天 Timeline 上，不再造 Goal 专属总结页面。Energy 推荐本版不改。

# 1.0.74 最终统计修正（2026-08-31）

本节覆盖前文中与 Timeline 时间平衡统计冲突的旧表达。

## 历史目标真实性

- 时间预设从现在起按 **ISO 周快照** 保存到 `GoalSettings.timePresetRevisions`。
- 同一周连续修改只更新本周快照，不保留逐次输入审计历史。
- Timeline 查询历史范围时优先使用该时间段当时生效的预设。
- 如果当时没有为某 Goal 设置预设，则按照**当前预设回算**；详情必须标注“当时未设 · 按当前预设回算”。
- 月 / 季 / 年跨多个预设版本时按各时间段分别计算后累计，不使用当前比例覆盖整个历史。

## 观测真实性

- TaskSession 只能证明“这段时间被记录到”，没有 TaskSession **不等于没有发生**。
- `实际` 在 Timeline 详情统一表述为 **已记录**。
- TaskSession 覆盖时间按区间并集计算，重叠 Session 不重复增加“记录覆盖”。
- Balance 状态：`平衡 / 偏高 / 偏低 / 记录不足 / 未设置 / 周期尚未开始`。
- 已记录已经超过 +10% 上界时可以确定“偏高”。
- 只有“已记录 + 全部未知时间”仍达不到 -10% 下界时，才能确定“偏低”。
- 只有未知时间不足以把结果推出 ±10% 区间时，才能确定“平衡”。
- 其它情况显示“记录不足”，不把未知时间按 0 处理。

## Timeline 主表达

- Timeline Goal 行主数字不再显示小时，而显示**相对预设差额百分比**：`(已记录 - 目标) / 目标`。
- 只有 Balance 结论可信时显示该百分比；记录不足显示 `—`。
- ±10% 内为绿色；高于或低于 ±10% 为红色；记录不足/未设置为中性。
- Goal 名称和图标保持原位置，仅降低不透明度；**不居中、不改变原表格结构**。
- 年 / 季继续沿用原 `月份 | 月度总结 | W1...W5` 表格，并增加 `本年度 / 本季度` 总统计行。
- 月 / 周 / 天继续沿用原 Timeline，左侧总结代表当前完整范围。
