# 深度收敛 V31 封版说明

V31 是 V26～V31 深度收敛的封版，不再继续大拆业务代码。它把前面五版的结构收益固化为文档、预算和 gate，使后续开发从设计阶段就能防止发散。

## 1. V26～V31 完成情况

| 版本 | 主题 | 完成状态 | 主要结果 |
|---|---|---|---|
| V26 | 语义函数收敛 | 已完成 | `compactText`、field token、multi value、theme path、timing 等有中心语义 |
| V27 | 大文件职责拆分 | 已完成 | `FloatingPanel`、`mui-theme`、`errorHandler` 拆成 facade + 内聚子模块 |
| V28 | View Config / Action 收敛 | 已完成 | `core/config/views` 与 `app/actions/recordCreate` 形成稳定扩展点 |
| V29 | Service Ownership 收敛 | 已完成 | `ItemService` 变薄；`ThemeManager` 运行时能力归入 core/theme |
| V30 | 类型债收敛 | 已完成 | src explicit any 从 648 降到 501，并进入预算 gate |
| V31 | 预算 / gate / 文档封版 | 已完成 | 新增 final gate、验收清单、开发防发散提示词、V31 final report |

## 4. 完成定义

V31 封版通过的最低要求：

```bash
npm run refactor:verify
npm run gate
npm run deep-refactor-final:gate
npm run any-budget:gate
```

本地完整验证要求：

```bash
npm ci
npm run typecheck
npm run build
npm run test:unit
npm run gate
```

当前源码包不包含 `node_modules`，因此 `typecheck`、`build`、`test:unit` 需要在本地安装依赖后执行。

## 5. 后续开发规则

1. 新功能先判断 ownership，再写代码。
2. 新增函数前必须搜索同义语义。
3. 能复用中心 semantics，就不要新增局部 normalize / parse / resolve / compact。
4. facade 只做出口与兼容，不写新业务逻辑。
5. shared 不是业务垃圾桶，只放通用 UI、hooks、utils、styles、types。
6. 单文件超过 300 行必须说明原因；超过 380 行优先拆分。
7. 不要继续大拆已经小而清晰的组件。
8. 预算只能降低，或在报告中明确说明为什么要调整。

## 6. 下一阶段建议

V31 之后不建议再开“全局整理版”。后续应该按功能或风险点做小批次：

```text
功能开发前：先跑 ownership 设计提示词
功能开发中：只在所属模块新增文件
功能开发后：跑 gate + final gate + 类型预算
发现发散时：只收敛具体语义，不全项目重排
```

适合继续做的小主题：

```text
剩余 explicit any 定点压缩
heatmap / timeline CSS 分区治理
局部重复 UI event handler 不强行抽象
按功能补单测，而不是继续改目录
```
