# Think OS 测试体系中文入门（v1）

这份文档只讲一件事：**怎样判断一个功能有没有被可靠地测试。**

## 1. 测试到底是什么

测试不是“写很多 `.test.ts` 文件”，而是：

1. 先规定什么结果才算正确；
2. 准备一个明确场景；
3. 执行程序；
4. 检查实际结果是否等于预期结果；
5. 以后代码改坏时，让测试自动报警。

例如：当前 Goal 没有直接启用的 Task 模板，而父 Goal 有模板。正确产品规则是：**不能偷偷继承父 Goal 模板，也不能猜测其它 Goal/RecordType。** 只要未来重构破坏了这个规则，对应测试就应该失败。

## 2. 常见英文名词，用中文记即可

| 英文 | 中文理解 | 主要回答的问题 |
|---|---|---|
| Unit Test | 小功能/规则测试 | 一个规则单独算得对不对？ |
| UI / Component Test | 界面交互测试 | 用户点、选、输入以后界面状态对不对？ |
| Integration Test | 模块组合测试 | 多个模块连起来以后数据还对不对？ |
| E2E | 真实流程测试 | 真正打开 Obsidian 后用户能不能完成任务？ |
| Smoke Test | 冒烟测试 | 插件至少能不能启动、加载、基本渲染？ |
| Regression Test | 防复发测试 | 修过的 Bug 会不会再次出现？ |
| Contract Test | 规则契约测试 | 核心产品规则会不会被重构偷偷改变？ |
| Migration Test | 升级测试 | 老版本数据升级后会不会丢失/变错？ |
| Coverage | 代码覆盖率 | 测试运行时碰到了多少代码？ |
| Branch Coverage | 分支覆盖率 | if/else 的不同分支是否都跑过？ |
| Mock | 假环境 | 用假的 Obsidian/网络/文件系统隔离测试 |
| Fixture | 测试样本 | 专门准备的 Vault、记录、配置、旧版本数据 |
| CI | 自动检查流水线 | 提交代码后自动跑检查和测试 |
| Gate | 质量门禁 | 不满足条件时不允许进入下一阶段/发布 |

## 3. Think OS 的六层测试

### 第 0 层：代码规则检查

检查 TypeScript、ESLint、架构边界、Record/Task/Energy 规则、CSS、Bundle 等。

回答：**代码结构有没有违反工程规则？**

### 第 1 层：小功能/规则测试

测试 Goal、Record、Field、Task、Energy、Template、Parser 等领域规则。

回答：**一个规则自己是否正确？**

### 第 2 层：界面交互测试

测试 Goal Cascade、Quick Input、Settings、View Editor、Timer Widget 等操作行为。

回答：**用户操作界面后，状态和可见结果是否正确？**

### 第 3 层：模块组合测试

测试完整数据链，例如：

`Template → RecordDraft → Codec → Markdown → Parser → RecordIndex → Query`

回答：**单独都正确的模块连起来后是否仍然正确？**

### 第 4 层：真实 Obsidian 流程

使用真实 Obsidian 自动操作插件，例如：

`打开 Quick Input → 选择 Goal → 选择任务 → 保存 → Timeline 出现 → 重启 → 仍然存在`

回答：**真实用户能不能从头做到尾？**

### 第 5 层：数据安全 / 升级 / 发布

检查写入失败、回滚、重启、迁移、旧 Vault、性能与发布包。

回答：**出现异常、升级版本或重新打开后，用户数据是否仍然安全？**

## 4. 覆盖率不等于功能覆盖

`代码覆盖率 90%` 不能证明 `90% 功能可靠`。

原因：某个函数的每一行代码虽然被执行过，但测试可能没有检查“文件是否真的写对、索引是否更新、重启后是否还能读到”。

Think OS v1 因此同时管理两种覆盖：

- **代码覆盖**：由 Jest coverage 报告；
- **功能覆盖**：由 `test/system/feature-test-map.json` 管理。

## 5. 功能必测八面

重要功能不要只测“正常成功”。按风险选择下面场景：

1. **正常**：正常输入能成功；
2. **边界**：空值、极端值、特殊输入；
3. **异常**：文件/网络/解析/保存失败；
4. **数据**：真正落盘后的内容正确；
5. **重启**：关闭再打开仍正确；
6. **回归**：过去修过的 Bug 不复发；
7. **升级**：老版本数据能升级；
8. **真实流程**：真 Obsidian 里用户能完整完成。

## 6. 风险等级

### P0：核心 / 数据安全

出错可能丢数据、写错数据、核心流程不可用。典型：Record 创建/修改/删除、GoalTemplate、Task、索引、迁移、设置仓储。

P0 应尽量覆盖：规则、组合、真机、持久化、重启、异常；涉及数据格式时再覆盖升级。

### P1：重要功能

出错严重影响使用，但通常不会直接破坏底层数据。典型：九种 View、Layout、Settings UI、AI、筛选器。

### P2：辅助体验

局部体验、工具或非关键适配。按实际风险选择少量高价值测试。

## 7. 怎样判断一个功能“有没有测试”

不要问“有没有 `.test.ts` 文件”，要问：

> 这个功能可能怎么坏？每一种高风险坏法，是否至少有一个测试会马上报警？

Think OS 第一版把这个问题固化为功能测试总账：

`test/system/feature-test-map.json`

每个条目包含：

- 功能编号；
- 功能域与功能名称；
- P0/P1/P2 风险；
- 对应源码入口；
- 必须具备的测试维度；
- 当前已有测试证据；
- 备注。

## 8. 开发一个新功能时的顺序

1. 在功能总账登记 `Fxxx`；
2. 判断 P0/P1/P2；
3. 写清楚最危险的失败方式；
4. 先补规则/组合测试；
5. 核心用户流程补 E2E；
6. 数据功能补持久化、重启、异常、升级；
7. Bug 修复必须补防复发测试；
8. 运行测试体系报告，确认没有遗漏。

## 9. 第一版可用命令

```bash
# 查看功能测试体系缺口，不阻断开发
npm run test:system

# 严格模式：任何 P0 必测维度缺失就失败
npm run test:system:strict

# 单元测试
npm run test:unit

# 组合测试
npm run test:integration

# 真实 Obsidian E2E
npm run test:e2e

# 统计整个 src 的代码覆盖，而不只统计被测试 import 的文件
npm run test:coverage

# 第一版发布验证（报告缺口但不因功能地图缺口直接失败）
npm run verify:release

# 未来 P0 补齐后启用的严格发布验证
npm run verify:release:strict
```

## 10. v1 的原则

第一版不会假装当前所有功能都已完整覆盖。

它先解决三个问题：

1. **把产品功能列全并编号；**
2. **明确每个功能应该测到什么深度；**
3. **让缺口可以自动统计，而不是靠记忆。**

之后新增测试的目标，不是追求“测试文件越来越多”，而是让 P0 功能逐步从“部分”变成“完整”。

## 11. v4 新概念：故障注入

故障注入不是等待 Bug 自己出现，而是在测试中主动制造故障，例如：

- 文件突然不存在；
- 用户编辑期间外部程序改写文件；
- JSON 损坏；
- 写盘失败；
- 回滚失败。

要验证的是：程序能否识别、保护原数据、给出恢复动作，并在条件恢复后继续工作。

## 12. v4 新概念：性能基线

性能基线回答：

> 数据规模变大以后，程序会不会从“正常”突然退化到“不可使用”？

不要把性能测试理解成追求固定毫秒。优先固定：

1. 数据规模；
2. 操作流程；
3. 正确性结果；
4. 一个宽松的灾难性回归上限。

Think OS v4 的第一批基线是 20,000 RecordIndex 和 1,500 Markdown 文件 DataStore。
