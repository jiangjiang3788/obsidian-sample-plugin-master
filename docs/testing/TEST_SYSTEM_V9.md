# Think OS 测试体系 v9：测试数据与故障实验室

## 一、v9 解决什么问题

v8 已经能回答“测试有没有运行、是否不稳定、有没有性能退化、失败现场在哪里”。v9 再往前一步，解决一个更实际的问题：

> 异常测试不能只靠临时 `mock`，也不能等真实用户遇到坏文件、同步冲突、磁盘失败、AI 超时后才知道程序会怎样。

因此 v9 建立**可重复故障实验室**。测试主动制造可控故障，验证 Think OS 是否做到：

1. 坏数据被隔离，而不是拖垮整个 Vault；
2. 冲突发生时不覆盖用户的外部修改；
3. 多文件写入中途失败时能回滚；
4. 回滚自身失败时明确报警，不伪装成功；
5. 已落盘但重新扫描失败时可以恢复；
6. AI 限流、坏 JSON、空响应、超时、取消都有确定行为；
7. 极端大输入不会出现灾难性卡死。

## 二、故障实验室由三部分组成

### 1. 固定坏数据样本

目录：

```text
test/fixtures/fault-lab/
```

当前固定样本包括：

- 缺少稳定记录 ID；
- 非法任务状态；
- 同步中断后的半写入 Record Block；
- 两个文件使用相同记录 ID；
- Task 引用不存在的 TaskSeries；
- 中文、Emoji、链接、标签、双冒号混合正文。

固定样本的价值是：同一个 Bug 在任何开发机、任何 CI 上输入完全一致。

### 2. 动态故障注入器

文件：

```text
test/support/faultLab.ts
```

它可以在**测试边界**制造：

- 第 N 次文件写入失败；
- 指定文件写入失败；
- 指定读取次数发生外部改写；
- 文件 stat 暂时获取失败；
- 超大正文确定性生成。

业务源码没有故障实验室专用分支。测试环境只是实现真实的 `VaultPort / FileStatPort` 边界，因此不会为了测试修改产品行为。

### 3. 故障场景总账

文件：

```text
test/system/fault-lab.json
```

每个场景必须声明：

- 故障编号；
- 中文名称；
- 风险等级；
- 故障是什么；
- 用户应该得到什么保护；
- 固定样本（如果需要）；
- 自动化测试证据；
- 对应的产品功能编号；
- 运行分组。

测试文件还必须显式写：

```text
@fault FL-XXX-001
```

所以不能只靠文件名猜“这个测试大概覆盖那个异常”。

## 四、几个关键故障实验

### 并发修改

```text
Think OS 读取旧内容
→ 同步软件/用户外部修改文件
→ Think OS 提交前再次校验
→ 发现内容不同
→ 阻止写入
→ 保留外部修改
```

预期错误：`record_write_conflict`。

### 多文件写入中途失败

```text
写 A 成功
→ 写 B 失败
→ 自动把 A 恢复到提交前
→ 整个操作返回失败
```

如果恢复 A 自身又失败：

```text
RecordTransactionRecoveryError
+
record_transaction_recovery_required
```

必须显式暴露“需要人工恢复”，不能给用户一个假的“保存成功”。

### 已落盘但扫描失败

```text
Markdown 写成功
→ FileStat 临时失败
→ DataStore 无法完成 post-commit rescan
→ 调用方收到明确失败
→ 文件仍保留在磁盘
→ stat 恢复
→ 手动/自动重新扫描
→ Record 重新进入索引
```

这是“数据已经存在，但内存索引暂时没跟上”的故障，不应该通过删除已写数据来掩盖。

### AI 超时

故障实验室不依赖真实网络波动。传输层故意保持 pending，直到 Think OS 自己的 `timeoutMs` 触发 `AbortController`，验证请求确实取消并返回 `AbortError`。

## 五、超大输入为什么单独放性能测试

v9 生成一条约 512KiB 的 Record 正文，验证：

- Markdown 可以被扫描；
- 稳定 ID 正常进入索引；
- 内容没有被截断；
- 本地测试耗时低于 3 秒的“灾难性预算”。

这个 3 秒不是正常性能目标，而是防止出现算法意外退化后几十秒甚至卡死。长期性能趋势仍由 v8 的性能历史机制负责。

## 六、中文命令

```bash
# 只检查故障总账、样本、@fault 追踪是否完整
npm --silent run 测试:故障实验室:审计

# 执行 19 个故障场景对应的核心/规模测试
npm --silent run 测试:故障实验室

# 不重新跑测试，只根据当前运行结果生成中文报告
npm --silent run 测试:故障实验室:报告

# v9 日常 CI 验证
npm --silent run 验证:CI:v9

# v9 完整发布验证
npm --silent run 验证:发布:v9
```

报告：

```text
reports/testing/fault-lab/故障实验室报告.md
reports/testing/fault-lab/故障实验室报告.json
```

## 七、和 v8 发布质量报告的关系

v9 把两条新运行证据加入发布质量报告：

- 故障实验室核心场景；
- 故障实验室超大输入。

如果只是测试文件存在、但本次没有实际执行，发布质量报告必须显示：

> 待补齐运行证据

不能因为 `@fault` 和样本都在就声称故障实验已经通过。

## 八、v9 的边界

v9 仍然不是“所有现实故障穷举”。例如：

- 真正磁盘空间耗尽；
- 操作系统进程被强杀；
- iCloud/OneDrive/Obsidian Sync 的具体竞态；
- 文件系统权限突变；
- 真实 AI 厂商区域性故障；
- 手机系统杀后台。

这些需要真实设备/系统级实验。v9 的目标是把**最重要、可确定复现的异常模式**先变成日常 CI 可以稳定执行的自动化资产。
