# Think OS 测试体系 v8：测试结果治理与发布质量报告

## 一、v8 为什么不继续堆功能测试

v7 已经把 93 个产品功能的 P0/P1/P2 必需测试维度全部纳入严格证据门禁。v8 的重点不再是“有没有测试文件”，而是回答另外五个长期问题：

1. 某个测试是不是偶尔通过、偶尔失败？
2. 哪些测试越来越慢？
3. 性能是不是连续几个版本都在退化？
4. 真机失败后有没有截图和页面现场可以复盘？
5. 发布前能不能用一份报告区分“通过、失败、尚未运行”？

因此 v8 建立的是**测试结果治理层**。

## 二、结构化测试结果与耗时

Jest 中文报告器现在同时生成机器可读结果：

```text
reports/testing/*-结构化结果.json
```

记录：

- 测试文件数、用例数、通过/失败/跳过；
- 总耗时；
- 每个测试文件耗时；
- 每个测试用例耗时；
- 最慢用例排行。

公开终端仍保持中文。源码里仍存在英文测试标题时，中文终端不会直接把英文标题刷出来，而显示“未中文命名的源码用例”；原始标题保留在结构化/技术结果中用于工程定位。

## 三、真实 Obsidian 失败现场

WDIO 真机测试新增 `afterTest` 现场采集。

测试失败时自动保存：

```text
reports/testing/e2e-artifacts/<本次运行>/
├── *.png                 # 失败截图
├── *-页面现场.html       # 当时页面 DOM / HTML
└── *-失败摘要.json       # 用例、耗时、错误、现场文件引用
```

同时每次真机运行生成：

```text
reports/testing/e2e-<套件>-结构化结果.json
```

包含每个用例耗时、Obsidian 版本、失败现场路径。

## 四、不稳定测试（Flaky）审计

“不稳定测试”指同一份代码、同一组测试，有时通过、有时失败。

v8 不通过自动重试把问题藏起来，而是显式重复执行后比较结果。

### Jest 稳定性

```bash
npm --silent run 测试:稳定性
```

默认重复 3 轮单元 + 组合测试，分类为：

- 稳定通过；
- 疑似不稳定；
- 稳定失败；
- 包含跳过。

报告：

```text
reports/testing/stability/jest/稳定性审计.md
```

### P0 真机稳定性

```bash
npm --silent run 测试:真机:稳定性:P0
```

默认构建一次后重复 2 轮真实 Obsidian P0 流程。测试失败时仍会保留截图/页面现场。

## 五、性能历史趋势

性能测试不再只有“低于 8 秒就算过”。v8 会额外记录机器可读性能指标：

- AI 本地检索建索引 / 查询；
- RecordIndex 20,000 条重建 / 查询；
- DataStore 1,500 文件扫描 / 查询 / 重建。

结果保存在：

```text
reports/testing/history/performance-history.json
reports/testing/history/performance-trend.md
```

判定分为：首次记录、稳定、需要关注、明显变慢、明显变快。

趋势警告只是历史回归信号；真正阻断仍由性能测试中的宽松灾难性预算断言负责，避免不同 CI 机器的毫秒差异造成误杀。

## 六、测试历史

Jest 和真机结构化结果都会汇总到：

```text
reports/testing/history/test-runs.json
reports/testing/history/test-trend.md
```

历史保留最近运行，能看：

- 最近通过/失败；
- 总耗时变化；
- 历史最慢测试。

GitHub Actions 用缓存恢复 `reports/testing/history`，使性能趋势不会因为每次 CI 都是干净机器而完全失忆。

## 七、发布质量报告

```bash
npm --silent run 测试:质量报告
```

输出：

```text
reports/testing/发布质量报告.md
reports/testing/发布质量报告.json
```

报告明确区分三种状态：

- **满足发布测试条件**：要求的运行结果全部存在且通过；
- **阻止发布**：已经有明确失败结果；
- **待补齐运行证据**：测试结构完整，但某些测试本次没有实际运行。

这个区分用于避免再次把“有测试证据”误说成“实际执行已通过”。

## 八、v8 CI

工作流：

```text
.github/workflows/think-os-test-v8.yml
```

### 日常提交 / PR

保持 v7 的严格功能地图、语法、工程质量、单元、组合、覆盖率、性能和 P0 真机。

### main / master

继续运行 P1/P2 真机。

### 每周 / 手动

额外执行：

- 大仓库真机；
- 最早/最新 Obsidian 兼容矩阵；
- Jest 三轮稳定性审计；
- P0 真机两轮稳定性审计。

### 最终质量汇总

CI 最后下载各 Job 的测试产物，生成统一的中文发布质量报告。失败截图、结构化结果和技术日志默认保留 21 天，最终质量报告保留 30 天。

## 九、主要中文命令

```bash
# 结果治理结构检查
npm --silent run 测试:结果治理

# 测试历史 / 性能趋势
npm --silent run 测试:趋势

# Jest 不稳定测试审计
npm --silent run 测试:稳定性

# P0 真 Obsidian 不稳定测试审计
npm --silent run 测试:真机:稳定性:P0

# 生成发布质量报告
npm --silent run 测试:质量报告

# v8 日常 CI 级验证
npm --silent run 验证:CI:v8

# v8 完整发布验证（很重）
npm --silent run 验证:发布:v8
```

## 十、质量边界

v8 仍坚持两条原则：

1. **结构完整不等于运行通过**。没有实际 Jest/WDIO 运行结果时，发布质量报告必须显示“待补齐运行证据”。
2. **重复重试不能掩盖 Flaky**。v8 的重复执行用于识别不稳定测试，而不是把第二次通过当成第一次失败不存在。

当前生成环境如果无法完成 `npm ci`，只能证明脚本、证据、配置和静态审计成立；完整运行结论必须由开发机或 CI 给出。
