# Think OS 测试用例标准（v1）

## 1. 一个好测试至少写清楚四件事

- **场景**：在什么前提下；
- **操作**：用户/程序做什么；
- **预期**：什么结果才算正确；
- **风险**：这个测试在防什么错误。

推荐采用“准备 → 操作 → 结果”的结构。

## 2. 命名规则

测试名称优先描述产品行为，不描述内部实现。

推荐：

```text
当前 Goal 没有直接 Task 模板时禁止创建任务
完成循环任务后生成下一次任务且保持 seriesId
保存失败时保留原记录并返回可恢复错误
点击二级 Goal 后第三列只显示它的直接子 Goal
```

不推荐：

```text
resolver test 1
should call foo
state is true
works
```

## 3. Bug 修复规则

任何真实 Bug 修复，原则上先新增一个能复现 Bug 的测试，再修代码。

目的：让这个坑以后永远有自动报警器。

## 4. P0 数据功能最低检查

涉及 Record / Task / GoalTemplate / Settings / Index / Migration 时，至少考虑：

- 正常创建/修改/删除；
- 无效输入；
- 写入失败；
- 索引同步；
- 重启恢复；
- 旧数据兼容；
- 重复执行是否安全；
- 原数据是否会被破坏；
- 真 Obsidian 主流程。

## 5. E2E 写法原则

E2E 测“用户旅程”，不要重复单元测试细节。

优先保护：

1. 插件启动；
2. Goal/GoalTemplate 配置；
3. Quick Input 创建 Record；
4. Task 完成/循环/Timer；
5. 九种 View 至少能展示关键数据；
6. Settings 保存并重启恢复；
7. 老版本 Vault 升级；
8. 索引重建；
9. AI 主流程（可使用可控测试服务/Mock，避免依赖真实付费接口）。

## 6. 功能总账更新规则

新增功能或删除功能时，同一个 PR 必须更新：

`test/system/feature-test-map.json`

已有测试证据放在 `evidence` 对应维度中。没有测试就保持为空，不允许为了“看起来完整”填一个无关测试文件。
