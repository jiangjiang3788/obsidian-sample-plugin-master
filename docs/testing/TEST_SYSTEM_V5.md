# Think OS 测试体系 v5：质量审计、全中文输出与 P1 扩展

## 一、为什么 v5 先停下来审计

v1-v4 已经建立了功能地图、数据安全、真实 Obsidian E2E、故障注入和性能基线，但本次复查确认：**“测试文件很多”和“测试体系合格”不是一回事。**

因此 v5 没有直接继续堆测试，而是先对今天形成的整套体系做质量审计。审计发现 v4 原版存在四类问题：

1. Jest / WDIO / 构建工具仍可能把英文技术输出直接显示到终端；
2. 旧的功能完整度只检查“证据文件存在”，证据口径偏松；
3. 个别证据分类错误，或组合测试过度 mock；
4. P1 真机套件最初只执行 AI Chat，一些新增 E2E 文件没有进入实际套件。

这些问题均已重做后，才继续 v5。

另外，v5 最终复核还专门检查了“审计工具本身”：临时语法检查曾因未传真实文件名而产生一次假阳性，确认后没有修改正常测试，而是增加正式 `测试:语法` 命令，确保以后用可复现的方法检查测试源码与测试脚本。

## 二、什么叫“所有测试输出中文”

公开测试命令的终端输出必须中文化：

- Jest 文件结果、用例汇总、失败标签使用中文；
- 常见断言失败尽量显示 `【期望】` / `【实际】`；
- Coverage 汇总使用中文；
- WDIO / Obsidian 真机测试使用中文运行包装层；
- E2E 前置构建也由中文包装层捕获，不把 Vite 等英文输出直接刷到终端；
- 性能基线和测试体系审计输出中文。

第三方英文堆栈、matcher 细节和构建日志不会删除，而是保存到 `reports/testing/*技术日志.txt`，供需要时定位。这样既保证使用者主要看到中文，也不丢失底层诊断信息。

中文入口示例：

```bash
npm run 测试
npm run 测试:单元
npm run 测试:组合
npm run 测试:覆盖率
npm run 测试:性能
npm --silent run 测试:体系
npm --silent run 测试:语法
npm --silent run 测试:真机:P0
npm run 测试:真机:P1
npm run 验证:P1:v5
```

## 三、证据口径已经重做

现在一个功能维度只有同时满足以下条件，才会被功能地图算作覆盖：

1. 证据文件真实存在；
2. 证据目录与测试类型相符，例如 unit 不能由 performance 文件冒充；
3. 文件有精确的 `@covers Fxxx/dimension` 声明；
4. 文件内真实存在测试用例。

自动命令：

```bash
npm --silent run 测试:证据同步
npm --silent run 测试:证据审计
```

这里的 `@covers` 表示“这个测试被设计来证明这个功能维度”，**不表示测试已经执行通过**。

## 四、今天审计后重做的典型问题

### VaultWatcher

原来 F122 的 unit 证据曾指向 integration 文件。v5 增加真正的 `test/unit/vaultWatcher.test.ts`，不再混淆分类。

### 大 Vault

原来 F132 曾拿 performance 文件同时冒充 integration。现在 performance 只承担性能证据，DataStore 组合链路由真正 integration 文件承担。

### Record 冲突恢复

原组合测试曾把冲突、扫描、重试结果都 mock 出来。现在改成真实：

```text
DataStore
→ RecordRepository
→ InputService
→ 磁盘内容变化
→ 冲突
→ 重新扫描
→ 同一更新重试
```

### P1 真机套件

v5 修正 `wdio.conf.mts` 的 `p1` 套件，确保 AI Chat、设置、GoalTemplate/FieldsEditor、精力快速采集、九视图等 E2E 真正被 `test:e2e:p1` 纳入。

## 六、当前功能地图

当前严格证据口径下：

- P0：40 项，**40 完整 / 0 部分 / 0 缺失**；
- P1：50 项，**42 完整 / 5 部分 / 3 缺失**；
- P2：3 项，0 完整 / 1 部分 / 2 缺失。

“完整”只代表这个功能要求的测试维度都有合格证据，不代表当前机器已经把测试跑绿。

P1 剩余真实缺口主要集中在：

- 精力管理/精力视图更深层真机行为；
- AI 批量确认与自然语言完整外部链路；
- 布局编辑器拖拽/缩放/复制删除与模块设置完整真机生命周期；
- 大 Vault 真实 Obsidian 慢速 E2E；
- 多 Obsidian 版本兼容矩阵。

这些不能靠“加一个文件”伪装完成。

## 八、当前环境的验证边界

本生成环境此前多次执行 `npm ci` 时超时，没有完整依赖，因此这里会严格区分：

- **已确认**：功能地图、证据分类、产品功能面、中文输出规则、TypeScript 语法、脚本语法；
- **不能宣称**：全部 Jest、Coverage、真实 Obsidian WDIO 在本环境已经实际跑绿。

最终是否“运行通过”，必须由依赖完整的开发机或 CI 给出。
