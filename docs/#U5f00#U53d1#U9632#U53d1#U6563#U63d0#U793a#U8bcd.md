# 开发防发散提示词

这份提示词用于新功能设计、代码生成和提交前 review。目标是在设计阶段规范 ownership、文件职责、函数复用和预算，减少后期集中整理。

## 1. 新功能设计前 ownership 审查

```text
你是这个项目的架构守门人。我要设计一个新功能：{功能名称}。

请先不要写代码，先输出设计审查：

1. 这个功能属于 core / app / features / platform / shared 哪一层？为什么？
2. 领域语义、用例编排、UI 展示、平台适配分别应该放在哪里？
3. 是否已有相同语义函数、service、model、public facade 可以复用？请列出候选模块。
4. 哪些逻辑不能放进 shared？哪些逻辑不能放进 core？
5. 给出建议目录结构、文件职责和每个文件的最大行数预算。
6. 给出 import 方向约束：允许依赖什么，禁止依赖什么。
7. 给出验收 gate：typecheck / build / test / gate 之外，还要检查哪些指标？

最后输出一个“可以开始实现 / 需要重新设计 / 需要先拆旧模块”的结论。
```

## 2. 写代码前防发散约束

```text
请按“先设计，后实现”的方式开发 {功能名称}。

硬性约束：

- 不新增 root public 大桶导出，优先使用模块 public facade。
- 不在 shared 放业务语义；shared 只放纯 UI、通用 hook、通用 utils、样式桥。
- 不在 feature 内重复 core 已有语义函数。
- 单文件超过 300 行必须解释，超过 380 行必须拆分。
- 新增函数前先搜索是否已有同义函数；如果已有，复用或扩展中心语义。
- 文件必须是 facade / types / semantics / model / view / hook / adapter / service / utils 中明确一种角色。
- 不允许一个文件同时承担 UI、持久化、平台适配、领域规则四种职责。
- 保留旧 import path 时，只允许做 compatibility facade，不允许在 facade 写新业务逻辑。

请先输出文件结构和职责表，等设计通过后再给代码。
```

## 3. 生成代码后的自检

```text
请审查刚才生成的代码，不要继续写新功能。

按以下清单检查：

1. 是否产生重复语义函数？列出所有 normalize / parse / build / resolve / ensure / compact / map 函数。
2. 是否已有同义函数可以复用？如果有，指出应该迁移到哪个中心模块。
3. 是否有大文件趋势？列出新增和修改文件行数。
4. 是否破坏层级依赖？core 是否依赖 app/features/platform？shared 是否依赖 app/core 业务？
5. 是否应该抽成 semantics / model / adapter / hook / service？
6. 是否出现 any、as any、unknown 未收窄？
7. 是否有 import path 绕过 public facade？
8. 是否有旧 facade 需要保留兼容？
9. 给出最小修复 patch，而不是重写整块代码。

最后输出：
- 可以合并
- 需要先拆分
- 需要重新设计
三选一。
```

## 4. 新增模块固定结构

```text
为 {模块名} 生成代码时，请强制遵守这个结构：

- public.ts / index.ts：只导出稳定 API，不写业务逻辑。
- types.ts：只放类型。
- semantics.ts：只放领域判断、归一化、解析、映射。
- model.ts：只放状态模型和纯计算。
- useXxx.ts：只放 hook 和副作用。
- XxxView.tsx：只放展示，不直接写持久化和平台 API。
- XxxService.ts：只放领域服务，不直接 import UI。
- adapter.ts：只连接平台或第三方库。

如果某个文件需要超过 300 行，请先拆分再输出。
如果某段逻辑不清楚应该放哪里，请先停止并给出 ownership 判断。
```

## 5. 提交前 reviewer 审查

```text
请作为 reviewer 检查这次提交是否会制造后期整理成本。

输出：

1. 新增文件职责表。
2. 修改文件行数变化。
3. 新增/修改函数清单，标记是否已有同义实现。
4. import 依赖方向图。
5. 可能变成大文件的风险点。
6. any / as any 变化。
7. public facade 是否合理。
8. 是否有 shared 被滥用。
9. 是否有 feature 私有逻辑泄漏到 core/shared。
10. 必须补的测试和 gate。

最后给出结论：
- 可合并
- 需要先拆分
- 需要重新设计
```

## 6. 固定开发流程

| 阶段 | 目标 | 使用提示词 |
|---|---|---|
| 需求阶段 | 判断功能归属和边界 | 新功能设计前 ownership 审查 |
| 设计阶段 | 输出目录结构、职责表、预算 | 写代码前防发散约束 |
| 实现阶段 | 按 facade / model / hook / service 拆文件 | 新增模块固定结构 |
| 自检阶段 | 查重复函数、大文件、依赖方向 | 生成代码后的自检 |
| 提交阶段 | reviewer 视角防后期返工 | 提交前 reviewer 审查 |

一句话原则：先定 ownership，再写代码；先查同义语义，再新增函数；先拆职责，再扩功能；shared 不是业务垃圾桶。
